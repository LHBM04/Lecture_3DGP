# TUK 리소스 바이너리 포맷 v1

## 사용 범위

- 모델: `.tukmodel`, 리소스 종류 `1`
- 메시: `.tukmesh`, 리소스 종류 `2`
- 머티리얼: `.tukmaterial`, 리소스 종류 `3`
- DDS 텍스처와 CSO 셰이더는 기존 형식을 유지한다.
- 폰트: `.tukfont`, 리소스 종류 `4`. 상세 규약은 [FontBinaryFormat.md](FontBinaryFormat.md)를 참조한다.
- 수학 타입의 기존 JSON 인터페이스는 유지한다.

## 공통 인코딩

모든 정수와 실수는 little-endian이다. 실수는 IEEE 754 binary32이며 NaN과 무한대는 허용하지 않는다.
문자열은 `u32 UTF-8 바이트 길이 + 해당 길이의 UTF-8 바이트`이며 널 종료 문자를 쓰지 않는다.
문자열 안의 널 문자와 잘못된 UTF-8은 허용하지 않는다.
고정 배열은 원소만 순서대로 기록하고, 가변 배열은 `u32 원소 개수 + 원소들`로 기록한다.
구조체 메모리, 패딩, 포인터를 그대로 기록하지 않는다.

파일 헤더는 패딩 없이 20바이트이다.

| 오프셋 | 타입 | 값 |
| --- | --- | --- |
| 0 | 4바이트 | ASCII `TUKR` |
| 4 | u32 | 리소스 종류 |
| 8 | u32 | 포맷 버전 `1` |
| 12 | u64 | 헤더 이후 본문의 바이트 크기 |

본문은 루트 객체 하나이다. 객체는 `u64 객체 본문 크기 + 필드 블록들`이다.
필드 블록은 `u32 필드 ID + u64 필드 데이터 크기 + 필드 데이터`이다.
필드 크기는 자기 자신의 ID와 크기 헤더를 포함하지 않는다.
필드에 객체를 기록하면 필드 데이터 안에 객체의 `u64 본문 크기`도 들어간다.
객체 배열의 각 원소도 각각 객체 크기 접두사를 가진다.

필드 순서는 자유롭지만 한 객체 안에 중복 ID와 ID `0`은 허용하지 않는다.
모르는 필드는 그 필드의 크기만큼 건너뛴다. 알려진 필드는 선언한 타입으로 정확히 끝까지 읽혀야 한다.
필수 필드가 없으면 실패한다. 선택 필드가 없으면 저장 데이터 구조체의 초기값을 유지한다.
기존 필드 ID의 타입이나 의미는 바꾸지 않는다. 호환되는 선택 필드 추가는 새 ID로 처리하고,
기존 의미 변경이나 필수 필드 변경에는 새 포맷 버전을 사용한다.

파일 크기는 최대 512MiB, 개별 문자열/가변 배열은 최대 16,777,216바이트/원소,
객체 중첩은 최대 128단계, 객체당 필드는 최대 1,024개이다.
C++ 입력은 문자열과 가변 배열의 누적 할당량도 512MiB로 제한한다.
모델 래퍼와 렌더 파트도 객체 깊이에 포함되므로 실제 노드 계층의 최대 깊이는 128보다 작다.

## 모델 스키마

모델 루트 객체의 필드 `1`은 최상위 노드 객체이다.

| 노드 필드 ID | 내용 | 타입 |
| --- | --- | --- |
| 1 | 이름 | 문자열 |
| 2 | 부모 기준 위치 | f32 × 3, x/y/z |
| 3 | 부모 기준 회전 | f32 × 4, Quaternion x/y/z/w |
| 4 | 부모 기준 크기 | f32 × 3, x/y/z |
| 5 | 렌더 파트 | 객체 가변 배열 |
| 6 | 자식 노드 | 노드 객체 가변 배열 |

모든 노드 필드는 필수이다. 메시가 없는 부모 노드는 빈 렌더 파트 배열을 기록한다.
배열 순서와 빈 노드도 보존한다. 부모 인덱스는 파일에 기록하지 않는다.
렌더 파트 객체의 필드 `1`은 메시 경로, 필드 `2`는 머티리얼 경로이다. 둘 다 필수 문자열이다.
로드한 계층은 기존 렌더링과 연결하기 위해 전위 순회의 `Submodel` 배열과 부모 인덱스로 변환한다.

## 메시 스키마

| 필드 ID | 내용 | 타입 | 필수 |
| --- | --- | --- | --- |
| 1 | 위치 | f32 × 3 가변 배열 | O |
| 2 | 노멀 | f32 × 3 가변 배열 | O |
| 3 | UV0 | f32 × 2 가변 배열 | X |
| 4 | 인덱스 | u32 가변 배열 | O |

현재 익스포터처럼 서브메시마다 별도 메시 파일을 만든다.
현재 엔진에서 사용하지 않는 탄젠트와 추가 UV 채널은 이번 스키마에 넣지 않는다.
필요해지면 새 필드 ID로 추가할 수 있다.
UV는 Unity 값을 그대로 저장하고 DDS 샘플링용 Y 반전은 기존처럼 C++ 로더에서 한 번 수행한다.

## 머티리얼 스키마

| 필드 ID | 내용 | 타입 | 기본값 |
| --- | --- | --- | --- |
| 1 | BaseColor | f32 × 4 | 1,1,1,1 |
| 2 | EmissiveColor | f32 × 4 | 0,0,0,1 |
| 3 | SpecularColor | f32 × 4 | 1,1,1,1 |
| 4 | Metallic | f32 | 0 |
| 5 | Roughness | f32 | 0.5 |
| 6 | 패스 | u32 | 0: surface, 1: skybox, 2: imageUI |
| 7 | 정점 셰이더 경로 | 문자열 | 필수 |
| 8 | 픽셀 셰이더 경로 | 문자열 | 필수 |
| 9 | 텍스처 연결 | 객체 가변 배열 | 빈 배열 |

텍스처 연결 객체의 필드 `1`은 `u32 슬롯`, 필드 `2`는 `문자열 경로`이며 둘 다 필수이다.
슬롯은 현재 `MaterialTextureSlot` 순서와 동일하게 BaseColor=0, Normal=1, Metallic=2,
Roughness=3, Occlusion=4, Emissive=5, Specular=6, Mask=7이다.
Height는 현재 렌더러가 사용하지 않으므로 이 슬롯 목록에 포함하지 않는다.
슬롯 중복, 범위 밖 슬롯, surface 이외 패스의 텍스처 연결은 허용하지 않는다.

## C++ 사용

리소스 스키마는 `ResourceMetadata.hpp`에 선언한다. `Serialize`는 필드 대응만 기술하며,
실제 읽기/쓰기는 공통 아카이브가 처리한다. 로더에 문자열 읽기, 태그 읽기,
개수 읽기, 바이트 경계 검사 같은 별도 유틸리티를 만들지 않는다.

```cpp
auto metadata = Serializer::Load<ModelMetadata>(
    path, static_cast<u32>(ResourceType::MODEL));

if (!metadata)
{
    return std::unexpected(metadata.error());
}
```

새로운 저장 데이터는 다음처럼 필드 목록을 선언하면 된다.

```cpp
template <class TArchive>
bool ExampleMetadata::Serialize(TArchive& archive)
{
    return archive.Field(1, name)
        && archive.Field(2, children)
        && archive.OptionalField(3, options);
}
```

`Serializer::Save(path, resourceType, metadata)`는 같은 필드 선언으로 저장한다.
공유 `Serialize` 인터페이스를 사용하기 때문에 저장 함수도 변경 가능한 객체 참조를 받지만,
출력 아카이브는 데이터 값을 변경하지 않는다.
실제 파일 오류는 `std::expected`로 반환한다.

리소스 경로는 Resources 기준 상대 경로이다. 예: `Meshes/Chi_Ha/Body.tukmesh`,
`Textures/Chi_Ha/Body_BaseColor.dds`, `Shaders/Standard.vert.cso`.
`ResourceMetadata`가 카테고리 디렉터리에서 루트를 찾고 상대 경로 정책을 적용한다.
파일 시스템 경로 정책은 범용 바이너리 Serializer와 분리한다.

## Unity와 기존 리소스 전환

Unity에서는 `TUKEntityExporter.cs`와 `TUKSerializer.cs`를 같은 Editor 어셈블리에 둔다.
Unity 수집 과정은 기존과 같고, 공통 `TUKSerializer`가 필드 크기와 중첩 객체 경계를 기록한다.
익스포터는 기존처럼 원본 텍스처를 복사한다. DDS 변환 기능을 새로 추가한 것은 아니므로,
Unity에서 새로 내보낸 텍스처는 기존 DDS 변환 과정과 최종 경로 반영이 필요하다.

기존 저장소 JSON은 다음 명령으로 별도 바이너리 파일을 생성한다.

```powershell
node ./Tools/ConvertResourcesToBinary.cjs
```

도구 자체 위치에서 프로젝트 Resources 경로를 구하므로 현재 작업 디렉터리에 의존하지 않는다.
다른 Resources 디렉터리는 첫 번째 인수로 지정한다. Node.js 내장 모듈만 사용한다.
기존 JSON은 삭제하지 않으며, 같은 이름의 바이너리는 재생성한다.
전환 도구는 기존 JSON 셰이더 상대 경로도 Resources 기준 경로로 정규화한다.
프로그램의 모델/머티리얼 참조와 프로젝트의 리소스 복사 패턴은 새 확장자를 사용한다.
빌드 및 실행 확인 후 기존 JSON의 삭제 여부를 결정한다.
